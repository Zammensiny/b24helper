КОМПЛЕКТ ДЛЯ ПОДКЛЮЧЕНИЯ АВТООТВЕТОВ: АВИТО → БИТРИКС → OPENAI
Редакция 3 от 23.10.2026, с учётом реальных диалогов. Подготовлены инструкция, политика, схема ответа, импорт каталога и сценарии проверки.
Это не работающий подключённый бот. Код интеграции и событие Битрикс не предоставлены; предположительная модель — gpt-4o-mini. Пользователь не раскрывает коннектор, повторно запрашивать его не нужно. Ни один ответ покупателю не отправлялся. Технические статьи ещё не загружены в базу знаний.

1. ФАЙЛЫ
system_prompt_openai_v2.txt — новая инструкция для OpenAI. Устанавливается в подходящее для выбранной модели поле инструкций (developer/system); API-параметры определяются после получения model ID и endpoint.
store_policy.json — согласованные условия и отмеченные незаполненные настройки. Передавать только нужную часть по намерению.
response_schema.json — схема Structured Outputs; Сохранены основные поля; добавлены nullable extracted_data для черновика заказа и источники manager_confirmations/order_context. Это изменение контракта ответа, валидатор приложения необходимо обновить. Обновить схему и валидатор приложения вместе.
import_catalog.py — работающий локальный импортёр XML, без сетевых интеграций. Python 3.10+. Сохраняет исходные номера/состояния, отдельные склады, аномалии и происхождение.
snapshot/ — результат обработки предоставленной выгрузки: 1780 позиций. Это снимок, не текущие остатки.
acceptance_cases.jsonl — ожидаемое поведение в диалогах. Это спецификация тестов, а не результаты прогона OpenAI.
test_import_catalog.py — автоматические проверки импортёра.
priority_router.py — исполняемый локальный приоритетный обработчик вложений; требует адаптера к реальному событию.
test_priority_router.py — проверки фото, PDF, неизвестных вложений, дублей и молчания при менеджере.
dialogue_examples_anonymized.jsonl — новые примеры стиля и логики с заменёнными личными данными.
order_flow.txt — оформление, оплата, адреса, несколько товаров и границы подтверждений.

2. КАК СДЕЛАТЬ ПОНИМАНИЕ КОРОТКИХ ФРАЗ (ПУНКТ 3 ИЗ ОБСУЖДЕНИЯ)
Хранить состояние отдельно от промпта, с ключом portal_id + channel/account + chat_id + session_id. История и поля одного покупателя не должны попадать другому.
Поля: order_id, order_lines, recipient_draft, current_vehicle, vehicle_source, payment_status, shipment_status, current_offer_id, listing_id, offer_mapping_source, requested_pickup_city, delivery_city, city_source, current_topic, pending_question, answered_questions, human_takeover, handoff_status, last_processed_message_id, policy_version, snapshot_source_id.
У каждого важного поля — происхождение и время обновления. Объявление и товар связывать таблицей platform_account + listing_id → offer_id; ID Авито, chat_id и offer_id не равны автоматически. Название не гарантирует точного совпадения. При отсутствии ID/связи — поиск кандидатов и одно уточнение.
Сначала выполнить priority_router по нормализованным метаданным: фото/вложения и менеджер имеют приоритет над FAQ. Затем для текстового сообщения распознать все намерения, города и указания на смену товара. Сервис обновляет состояние по подтверждённым событиям и явным словам клиента; вывод модели не может сам выставить актуальность остатков, human_takeover=false или handoff_status=accepted.
«Есть?» относится к текущему однозначно выбранному товару. «А 0AM325025D?» означает новый поиск, даже в старом объявлении. «А в Екб?» меняет склад, не товар. «Отправить в Омск» задаёт город получения и не меняет склад выдачи.
Код kras — Краснодар; безопасные явные названия: Краснодар, Крд, Яблоновский. «Крас», «Красе» неоднозначны без контекста, уточнить «В Краснодаре?». Никогда не превращать явный Красноярск в Краснодар. Числовые/OEM-коды не исправлять по словарю опечаток.
Обрабатывать составные вопросы: «торг есть и в Красе есть?» — ответить про торг и отдельно проверить город/остаток. Шаблон по одному найденному слову не должен поглощать остальной запрос. Присланные фото, прямая просьба человека и активный менеджер имеют приоритет над FAQ.
Для короткого однозначного FAQ применить готовый ответ из policy, без каталога, веб-поиска и вызова OpenAI. Неоднозначные и составные сообщения — один вызов модели с минимальным нужным контекстом либо комбинирование проверенных обработчиков. Не вводить обязательную цепочку из трёх LLM-вызовов «классификация → поиск → переписывание».
Словарь примеров для распознавания: часы — «до скольки», «режим», «в воскресенье»; торг — «скинешь», «уступите», «крайняя», «торг»; наличие — «есть?», «налчии», «на складе»; самовывоз — «заберу», «подъеду». Эти слова не самостоятельные правила: «когда скинете фото» не вопрос о торге, «есть ли торг» не вопрос об остатке.

3. БИТРИКС: ЧТО ИМЕННО ПОДКЛЮЧИТЬ
Официальный сценарий для нового бота: зарегистрировать бота с поддержкой Открытых линий, подключить его к нужной линии, принимать события сообщений, отвечать в текущую сессию, передавать оператору при необходимости. Конкретная версия API должна соответствовать существующей интеграции.
В актуальном примере Битрикс используются imbot.v2.Bot.register, ONIMBOTV2MESSAGEADD и imopenlines.bot.session.message.send; передача — imopenlines.bot.session.operator или imopenlines.bot.session.transfer. История доступна через методы Открытых линий. Наличие ID объявления и города зависит от вашего коннектора Авито: по словам «всё из Открытой линии» этого установить нельзя.
Разработчик должен проверить реальную структуру входящего события и метаданных чата в своей реализации, без повторного запроса владельцу раскрыть коннектор. Удалить токены, вебхук-URL, телефон, ФИО и прочие персональные поля. Оставить названия полей, пример текстового сообщения, типы ID и доступные метаданные объявления. При необходимости второй пример — сообщение оператора.
Сервис проверяет источник события, сохраняет вход в устойчивую очередь и быстро подтверждает приём. Ключ идемпотентности: portal + connector/account + chat + message_id + revision. Не отвечать на собственное сообщение, служебное уведомление и реплику оператора.
Проверить human_takeover до генерации И перед отправкой: менеджер может подключиться, пока модель отвечает. Обновление блокировки сериализовать для каждого чата. Устаревший подготовленный ответ отменять, если его уже заменило новое сообщение/товар/действие менеджера.
При нескольких коротких сообщениях подряд допустим небольшой настраиваемый сбор пакета (пример для теста: 0,5–1 секунды, не бесконечный сброс таймера). Это необязательный баланс полноты и задержки; одиночный FAQ может отвечать сразу.
Ответ модели не выполняет действий. Приложение валидирует форму, факты, источники и идентификаторы, затем отправляет reply. Сначала передача оператору, потом сообщение об успешной передаче. При ошибке отправки/таймауте повторять контролируемо, сверяя уже созданные сообщения; не считать ответ API доказательством фактического получения покупателем.

4. ИМПОРТ ПРАЙСА
Команда из папки комплекта:
python import_catalog.py '/путь/export.xml' './snapshots/НОВАЯ_ВЕРСИЯ' --price-type retail --price-type-source owner-policy-2026-10-23-v3
python -m unittest discover -v
Импортировать при публикации новой выгрузки, не при каждом вопросе покупателя. Хранить последнюю исправную версию. Сначала прочитать и проверить новый файл в отдельном каталоге; убедиться в наличии manifest.json, контрольных суммах и ожидаемой структуре; затем одной транзакцией переключить ссылку активной версии/таблицы в приложении. При ошибке оставить старую и отметить давность.
Индекс: точный offer_id и номера с сохранёнными оригиналами; дополнительный поиск по названию/коробке. Для номера можно индексировать верхний регистр без пробелов/дефисов, но не заменять O/0, I/1 и окончания. Не использовать векторную похожесть как доказательство равенства номеров.
Весь JSONL не передавать в каждый запрос. При известном offer_id достаточно одной позиции. Для подбора — несколько релевантных кандидатов. Общие рекламные абзацы по умолчанию не включать. Исходный description сохранён для проверки технических ограничений и разночтений.
Дата XML: 2026-10-23 16:51, часовой пояс не указан. imported_at_utc — только время выполнения импортёра. Ни одна из дат не доказывает время пересчёта остатков в учётной системе. До уточнения export timezone не вычислять точный возраст по локальному времени как по UTC.
Дважды в неделю — режим обновления снимка; 3–4 дня между обновлениями возможны даже без сбоя. Для уверенного ответа «есть прямо сейчас» нужен более частый источник свободного остатка либо проверка менеджера. Предлагаемая следующая доработка — отдельная лёгкая выгрузка цены/свободных остатков каждые 15–60 минут, если это поддержит учётная система; это предложение, не настроенное расписание.
snapshot_quote_allowed и price_snapshot_quote_allowed вычисляет приложение с учётом согласованного срока давности, завершённости импорта и аномалий. Пока предельная давность, часовой пояс и учёт резервов не согласованы — только историческая формулировка с датой последнего файла, без обещания выдачи. Вопрос «сегодня заберу» требует подтверждения доступности.
available=true во всех 1780 позициях означает общий флаг; в Краснодаре у 375 позиций ноль, в Екатеринбурге у 398 ноль и у одной минус. Проверять конкретный stock.code. Отсутствующая строка не равна нулю, а пропавший из новой выгрузки offer не доказательство распродажи.
Две нулевые цены: 61730 («Герметик тест») и 62183 (фрикционы раздатки ATC35L/ATC45L). Не предлагать бесплатно. 61730 помечена возможной тестовой: исключить из автоматических рекомендаций, сохранить в исходных данных.
Остаток -1 у 56769 на ekb: блокировать утверждение по этому складу и направить на проверку, не менять другие положительные остатки. Не скрывать аномалию округлением к нулю.
1675 описаний упоминают скидки; 1661 — любую ТК. Действующая политика владельца: без торга, СДЭК, Авито пока не подключено. На уровне бота использовать policy; исходные карточки этим комплектом не редактировались.
По сравнению со старым JSONL добавлено 56 ID, отсутствуют 4; чистый прирост 52. Старые метки противоречий состояния нельзя механически переносить на новые тексты: описания изменились. Автоматический аудит здесь не подтверждает техническую правильность всех товаров.

5. OPENAI
По словам владельца модель, вероятно, gpt-4o-mini; точное значение model и endpoint разработчик проверяет в настройках. Официальная страница подтверждает Structured Outputs и помечает эту модель Deprecated: доступность текущего вызова и дальнейший выбор нужно проверить перед запуском, автоматически модель не заменяли. Не переносить temperature, лимиты и параметры reasoning с Qwen или другой модели без проверки поддержки. Для простых сообщений — шаблон либо недорогая быстрая модель, выбранная по проверке ваших сценариев. Для сложных вопросов — отдельная ветка с проверенными данными или менеджером.
Использовать Structured Outputs по response_schema.json, если выбранная модель/API это поддерживает; обрабатывать refusal, обрыв и таймаут отдельно. Схема гарантирует форму, не истинность. Для FAQ без LLM итоговый объект формируется кодом и проходит те же проверки перед отправкой.
Не генерировать длинное manager_summary для обычного FAQ. Источник факта проверять в коде; модель не выставляет live_data.valid=true. Историю передавать достаточную для текущей темы, сохраняя важные уточнения в состоянии. Стабильные инструкции и схемы ставить перед изменяемыми данными для кеширования поддерживаемыми моделями.
Измерять received_at, processing_start, lookup_end, model_start/end, send_start/end; отдельно фактическую задержку канала Авито. Сравнить p50/p95 для FAQ, наличия и подбора. Цель теста для локального FAQ — до 1 секунды работы обработчика без сетевой доставки; это ориентир, не измеренный результат. Искусственные паузы «чтобы выглядело как человек» не добавлять.

6. ТЕХНИЧЕСКИЕ МАТЕРИАЛЫ
Рекомендуемая база: отдельные небольшие фрагменты по коробкам/узлам, с URL, заголовком, датой получения, исполнением/годами/приводом, типом источника и статусом проверки. Искать по необходимости только для технического вопроса. Не открывать интернет ради графика или торга.
Владелец подтвердил transopt.net и zapakpp.ru. С transopt.net разрешены только статьи; веб-каталог, цены и остатки с сайта не загружать. Данные о товарах берутся из предоставленного XML. DRIVE2 при проверке не удалось прочитать через доступный инструмент: база статей не загружена.
Для карточек из XML и разрешённых статей: источник сведений о товаре и объяснений, не автоматическое доказательство совместимости всех перечисленных номеров. Для чужих статей: сначала проверка области применения. Для DRIVE2: личный опыт/исследовательская зацепка, нельзя на его основании гарантировать совместимость, момент затяжки или ремонтный допуск. Ссылки производителя и сервисные документы имеют приоритет для точных технических параметров.
Разрешение домена не заменяет проверку конкретной публикации. Не обучать модель заново для каждой статьи: индексировать разрешённый материал и передавать релевантный фрагмент. Цена и остаток вашего магазина всегда из вашего источника, не из чужой карточки.

7. ЧТО ПРОВЕРИТЬ РАЗРАБОТЧИКУ ПЕРЕД ПОДКЛЮЧЕНИЕМ
1) Точное значение модели и endpoint в имеющихся настройках; предположение владельца gpt-4o-mini не считать подтверждением.
2) Адаптер реального события Битрикс: сообщения покупателя/оператора, изображения, PDF, delayed file metadata, listing_id, город, статус менеджера. Владелец коннектор не раскрывает — это не мешает подготовке логики, но боевое подключение не выполнено.
3) Цены XML подтверждены как розничные. Как учитываются резервы, часовой пояс XML и допустимая давность — пока неизвестно; сохранить режим ответа по снимку.
4) График, адреса из XML, доставка СДЭК и отсутствие торга уже заданы. Под заказ не работаем — добавлено по повторяющимся примерам.
5) Реквизиты, стоимость довоза до ТК, тариф СДЭК, срок отправки и гарантию подтверждает менеджер конкретного заказа. Нельзя брать их из исторических диалогов как общую политику.
6) Домены подтверждены; transopt.net — только статьи. Техническую базу ещё нужно наполнить и проверить.
До живого включения прогнать acceptance_cases.jsonl на выбранной модели и реальном обработчике, затем в тестовом чате. Обязательно проверить молчание при менеджере, составные вопросы, отсутствие скидок, город склада, ошибки прайса, устаревший снимок и повторы событий.
