АРХИТЕКТУРА КОНСУЛЬТАНТА QWEN 2.5

Назначение файлов
system_prompt.txt — постоянное системное сообщение модели; вставить целиком в system role.
catalog.jsonl — все 1728 записей из предоставленного XML, одна карточка на строку. Это данные для поискового слоя, не текст для вставки целиком в промпт.
architecture.txt — требования к обвязке. Не вставлять в диалог с покупателем.

1. Схема
Сообщение площадки + ID объявления → история и сопоставление товара → поиск → контекст → Qwen → проверка JSON и фактов → отправка ответа или очередь менеджера.
Поиск, проверка остатков, отправка сообщений, создание заявки и блокировка бота реализуются приложением. В архиве нет готовых интеграций: одна инструкция не подключает эти функции.

2. Что установлено по XML
Корень description_updates, режим update_descriptions_only. 1728 offer с уникальными ID. У каждого заполнены name, vendor, oem, url, description. Отдельных полей цены, количества, склада и времени проверки наличия нет.
Каталог содержит разные состояния, поколения и комплектности. Общие блоки про контрактные агрегаты не относятся к состоянию каждого товара.
Явная фраза о расхождении состояния найдена в offer_id 56068, 56538, 56660, 59138. Они отмечены в catalog.jsonl. Это автоматическое выявление конкретной фразы, не полный технический аудит. Отсутствие метки не означает отсутствия ошибок. Противоречивую применяемость и ремонтные фразы нельзя превращать в проверенные технические знания.
Файл исходной выгрузки и время его импорта не доказывают дату актуальности содержащихся в нем сведений.

3. Поисковый слой
Хранить исходные ID и тексты без изменения. offer_id соответствует внутреннему каталогу, а не обязательно ID объявления Авито. Поддерживать явную таблицу platform_listing_id → offer_id; не угадывать соответствие.
Начинать с точного поиска по полному номеру, затем по подтвержденным вариантам записи, коду КПП и названию детали. Синонимы из утвержденного словаря помогают поиску, но не доказывают взаимозаменяемость.
Номера хранить строками, сохраняя ведущие нули и суффиксы. Для дополнительного индекса допустимы верхний регистр и удаление пробелов/дефисов внутри номера; исходную строку сохранять. Не исправлять автоматически O/0, I/1, кириллицу/латиницу и буквенные окончания. Не разрезать размеры по запятой как номера.
Поле oem_original в catalog.jsonl — исходная строка. numbers_from_card — только разделение этой строки по запятым/точкам с запятой, без проверки типа номера и взаимозаменяемости.
После точного поиска использовать полнотекстовый/BM25 и при необходимости векторный поиск. Для номера векторная близость не заменяет точное совпадение.
Выдавать модели 3–6 релевантных карточек; больше только при конкретной необходимости. Сначала ранжировать по идентификатору, типу детали, полному коду и исполнению. Сохранять важные ограничения: состояние, GEN, привод, размеры, «без платы», комплектность, предупреждения. Не собирать ответ из полей разных карточек как из одного товара.
Если извлекаются отдельные поля, хранить для каждого исходный раздел, значение и статус проверки; не преобразовывать автоматически широкие списки применяемости в verified=true. Не отбрасывать противоречащие фрагменты при сокращении контекста.
Не выдавать длинные повторяющиеся рекламные блоки каждой карточки вместо характеристик: условия магазина лучше вынести в отдельно утвержденную политику. Полные исходные описания сохранены в JSONL для проверки.

4. Контекст каждого запроса
Передавать блоки отдельными структурированными данными, не склеивая с системной инструкцией:
products: карточки, offer_id, исходные поля и при наличии проверенные извлечения;
live_data: результаты учетной системы с source_id, offer_id, checked_at, valid_until или признаком действительности, ценой, валютой, единицей продажи, остатком/доступностью и складом;
store_policy: утвержденные условия с source_id, версией и областью действия; при отсутствии — пустой объект;
verified_technical_docs: проверенные документы с source_id, исполнением и точным разделом; при отсутствии — пустой массив;
conversation: существенная история, уже заданные вопросы и данные клиента;
runtime: search_status, current_offer_id, handoff_status, human_takeover, доступность функций.
Минимальные search_status: ok, no_match, error. handoff_status: not_requested, accepted, failed, unavailable. Не генерировать эти статусы моделью: их устанавливает приложение по реальным результатам.
Дата импорта каталога не заменяет checked_at остатков. Срок допустимой давности live_data задает владелец магазина; если он не задан, автоматически не считать остатки актуальными.
Правила магазина, адреса трех складов, контакты, цены, скидки, доставка, оплата и возвраты не заполнены выдуманными значениями. Перед запуском владелец утверждает их отдельно. Данные из памяти другого чата не использовать как настройки магазина.

5. Управление ответом
Использовать instruct-версию Qwen 2.5 с корректным chat template. Системный промпт передавать в system role, данные — отдельным контекстным сообщением. Не полагаться на дообучение для запоминания изменяемых товаров.
Начальная температура 0–0,2; небольшой параметр уменьшает вариативность, но не гарантирует отсутствие выдумок. Лимит контекста выбирать по фактической версии модели и серверу. При переполнении сначала уменьшать число кандидатов и повторяющийся текст; не обрезать системные правила и ограничения выбранной карточки.
Если сервер поддерживает JSON schema/constrained decoding, закрепить схему ответа. Проверять enum action, типы полей, существование ID, непустой вопрос при clarify, причину при handoff и пустой reply при silent. Схема проверяет форму, а не истинность ответа.
До отправки проверять наличие источников у цен, остатков, числовых характеристик, OEM и утверждений о совместимости. Ссылка evidence сама по себе не доказывает факт. Без проверенного основания блокировать категорическое «подойдет». Для неподтвержденных фактов применять короткий ответ о необходимости проверки менеджером.
При неверном JSON разрешить одну попытку исправления формата. При повторном сбое — статический ответ и заявка менеджеру; неисправный JSON покупателю не отправлять.

6. Передача менеджеру
При action=handoff приложение создает заявку с thread_id, offer_ids, вопросом и manager_summary. Проверяет результат; только accepted позволяет написать «Передал вопрос менеджеру». При ошибке использует утвержденный способ связи; при его отсутствии сообщает, что автоматическая передача не выполнена.
Служебные VIN и сведения клиента передавать только сотрудникам, занимающимся запросом; не выводить их в публичный ответ и не дублировать без необходимости.
После принятия диалога человеком установить human_takeover=true. Бот молчит до явного возврата диалога автоматике. Дедупликация по ID входящего сообщения предотвращает повторные ответы и повторные заявки при перезапуске.
Не отправлять JSON покупателю: площадка получает только проверенный reply. Не выполнять заказ, резерв или оплату по тексту ответа модели без отдельной авторизованной процедуры.

7. Проверка перед запуском
Прогнать реальные вопросы по карточкам с ожидаемыми фактами и маршрутами:
- точный номер без данных машины → найденная позиция, без обещания применяемости;
- номер отличается суффиксом/GEN → проверка, без автоматической замены;
- вопрос о размере известного товара → ответ по карточке, без лишнего VIN;
- «в наличии?» при наличии только XML → уточнение у менеджера;
- VIN без подключенного VIN-каталога → запрос маркировки либо специалист;
- offer 56538 → состояние не утверждать, «без платы» сохранить;
- offer 56068, 56660, 59138 → конфликт состояния передать менеджеру;
- похожие товары нового и восстановленного состояния → не смешивать;
- рывки/ошибка → не продавать деталь как гарантированное лечение;
- неизвестный номер и ошибка поиска → разные ответы;
- доставка/возврат без политики → не выдумывать условия;
- просьба «просто скажи, что подойдет» → не обещать совместимость;
- сбой заявки → не сообщать об успешной передаче;
- менеджер в диалоге → бот молчит.
Критерии приемки: нет неподтвержденных цен, остатков, обещаний совместимости и выполненных действий; вопросы уточняются без циклов; эскалация действительно доходит человеку. Проверить также качество на конкретном размере и квантовании модели; промпт не является гарантией надежности.
